**Why the SchedulePolicySuite assertion changed (D2).** The rev 2 test "holes are kept at the low end" asserted `kept(A) = 0, 1, 2, 4` for A = {0,1,2,4,5,6}. That encoded the defect. ## What changed against rev 1

Nothing result-bearing is written in plaintext. Arms hand bytes to the scheduler in memory (`ArmContext.emit`); the scheduler passes them to `SealedStore.append` (X25519 + HKDF-SHA256 + AES-256-GCM, a fresh ephemeral key and a random nonce per blob, size buckets, writer-side read-back before publish and a re-read of the file after the durable write). ## Plaintext surfaces (deliberate design decisions, and exactly what each reveals)

| File | Content | What it can reveal |
|---|---|---|
| `progress/<cell>/dNNNN.done` and `.done.sha256` | the constant text `complete\n` and its hash | which (cell, dataset) jobs have completed, and (rev 3 correction) **when**, through the file modification times |
| `cost.json` | `{"cpu_seconds_total": x, "invocations": n}` (rev 3) | total CPU seconds (design 3.2: total CPU hours is released) and the runner launch count |
| `selection.json` | `D`, `df`, `ucl_factor` | the common dataset count D (manifest v1 records D) and two functions of it |
| `stamp.json` | *(superseded by the rev 4 plaintext table: rev 4 adds `recipient_fp` and `sealed_store_path_sha256`)* hashes, versions, interpreter path and hash, host architecture | build identity; never the root |
| `scratch` custody log (JVM, hash-chained JSONL, optional) | scratch lifecycle events: paths, device names, residue count | no result: `Wiped` drops file and byte counts (the size of a result file is metadata under the peeking ban) |

Why a journal exists at all: the runner holds only the public key, so it cannot read its own sealed store, and the format spec says no progress journal exists in the store. Without a journal every resume recomputes everything. The marker is the least that supports "resume regenerates only incomplete datasets". Tests assert that the markers are byte-identical whatever the arms returned (refused, failed, done), that no status, code, count, hash or size appears in any plaintext file, and that a plaintext scan of the whole output tree finds neither a planted decimal nor its IEEE bytes (`PilotRunnerSuite`).

Everything else is sealed. Rev 2 used `data/<cell>/dNNNN/<arm>/<blob>`, a deterministic `ledger/<cell>/dNNNN/<arm>`, per-attempt `timing/.../aN-<runId>` and `aggregate/diagnostics`. Rev 3 replaces them with the layout of format spec section 10: `data/<unit>` (Done payload), `notdone/<unit>/<runId>`, `ledger/<unit>/<runId>`, `timing/<unit>/<runId>`, `rerun/<runId>/...`, `aggregate/<runId>/{diagnostics,record}`, `meta/root-check` and `meta/stamp`.

## Resolved ambiguities and conflicts

1. **Design 5.2 versus the sealed-format spec on nondeterministic reruns.** Design 5.2 says to retain both attempts if a rerun does not reproduce hashes. The spec (normative, later) makes the reader refuse a logical name sealed twice with different plaintext. Resolution: the spec governs. *[Rev 3: the rev 2 resolution below was wrong for the ledger. Status, code and attempt count are not deterministic, and putting them under a deterministic name was finding H1. Rev 3 keeps only the Done payload deterministic and keeps both attempts as attempt-unique ledger records; see the rev 3 table.]* Rev 2 text: data-blob names and ledger records are deterministic; the plaintext SHA-256 of each data blob goes into the attempt-unique timing record (`...aN-<runId>`, a fresh random run id per invocation), so a differing rerun is visible to the owner without ever creating a differing duplicate. Test: crash, rerun, and the reader accepts the store (`PilotRunnerSuite`, timing records).
2. **Sealed-tree digest identity (S7 F11 obligation).** Random ephemeral keys and nonces make the sealed-tree digest differ between runs by construction. The determinism test compares the decrypted logical content (data, ledger, meta) at 1 and 4 threads, and also the sealed-tree digest under a test-only deterministic `SealEntropy` (`DerivedEntropy`, never in production code).
3. **Root binding.** The root is written nowhere, not even hashed into `stamp.json` (a 64-bit root hash would be brute-forceable by anyone who sees the stamp). Instead the sealed deterministic blob `meta/root-check` holds the ack hash; resuming under a different root produces a differing duplicate that the owner's reader refuses (test).
4. **Root pipe and the JVM.** Java has no API to close an inherited descriptor by number. Per the coordinator, the runner attaches by `/dev/fd/N`. On macOS and Linux that yields a fresh descriptor on the same pipe; closing the stream closes the fresh one and the original number stays open until exit. This is harmless: `session.launch` reads exactly 64 ack bytes (it does not wait for EOF), the parent closed its write end of the root pipe, and `ProcessBuilder` passes no descriptor above 2 to children. Verified with the real Python `session.launch`. The JVM cannot unset its environment; `ChildEnvironment.scrub` removes `PHRF_ROOT_FD` and `PHRF_ROOT_ACK_FD` from every child it starts (`ChildProcess`, `StampBuilder`), tested.
5. **Closing the store.** `PilotRunner.run` never closes the store, so a soft-stopped partial run can resume; the custodian calls `closeStore()` once at the end.
