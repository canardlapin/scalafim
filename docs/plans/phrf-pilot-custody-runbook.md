# PHRF pilot custody runbook (rev 2, after independent review of 77b49dc4)

Design: `docs/plans/phrf-pilot-runner-design.md` v2.1, section 4 (custody, seeds, F10), slice S9. Protocol: section 8. Custodian: **backlog-worker-20260930**, who is not an author of the runner, generator, scorer or aggregator. Tooling: `tools/phrf-comparison/custody/` (`python -m phrf_custody`, venv from `requirements.lock`). Sealed blob format: `docs/plans/phrf-pilot-sealed-format.md`.

## 0. Threat model, stated plainly

All agents run as one OS user, so file modes cannot separate authors from the custodian. Separation rests on:

1. **Encryption to an owner-held public key.** The private key never exists on this machine and no agent generates, stores or handles it. Raw results are encrypted at write time (format spec), so plaintext raw results never reach disk.
2. **A commit-reveal custodian secret** (owner decision, Mote bd-01M3TNWW). `root = SHA-256(v0_hash || beacon_A || secret)`; v0 commits only `SHA-256(secret)`. The 32-byte secret is generated in the custodian process, sealed to the owner key, and revealed by the owner at unseal. Without it nobody, authors included, can regenerate the pilot data from public inputs.
3. **The custodian computes the whitelist in-run** and publishes only the whitelist plus digests.
4. **A rule plus an audit** (sections 3 and 5): authors and agents other than the custodian do not run, read or observe anything of the pilot; process and open-file snapshots are hashed into the custody log. The ban on peeking is enforced by that rule and that audit, not by file modes. This is not a defence against a hostile custodian or against a same-user process that ignores the rule; it makes violations visible.

Residual exposure, recorded and accepted:

- **Process memory and swap.** The secret, root64 and plaintext results exist in the memory of the custodian's processes. Same-user processes can in principle read that memory or the swap file. Mitigate: no other agent sessions run during the pilot (section 5), disable or encrypt swap (macOS: FileVault on; do not run a debugger or `vmmap`/`lldb`/`sample` on custodian processes), and do not take core dumps (`ulimit -c 0`).
- **Plaintext on disk.** The runner has no staging directory: it encrypts every result at write time. Outside the sealed store it writes only `stamp.json`, `cost.json` (total CPU seconds and the invocation count), `selection.json` (D, df, UCL factor) and constant-content journal markers `progress/<cell>/dNNNN.dispatched` and `progress/<cell>/dNNNN.done` (format spec section 10). None of these holds a result, but the markers' modification times reveal when each job was dispatched and completed. **The runner output directory must therefore lie inside the custodian work directory** and falls under the no-peeking rule of section 3. Overwrite-then-unlink in `seal` does not guarantee erasure on journaling or copy-on-write filesystems.
- **Spotlight and other indexers.** `.metadata_never_index` is not honoured on current macOS. Instead put the runner output directory (which holds the sealed store) inside a directory whose name ends in `.noindex` (for example `pilot-work.noindex/`), and/or turn indexing off for the volume (`sudo mdutil -i off <volume>`, owner-run), and exclude both from Time Machine and any cloud sync. Check with `mdutil -s <volume>` and record the output in the start snapshot.
- **Sleep and reboot.** Run the session under `caffeinate -i -s` (for example `caffeinate -i -s python -m phrf_custody session ...`) so the machine does not sleep between v0 and round A or during the run, and disable automatic restarts for updates. **A reboot, logout or crash of the session process loses the secret**, which lives only in that process's memory. Recovery is only through the owner's stdin path (section 6); if the owner is unavailable the pilot is void.
- **The root64 reaches the runner through an inherited pipe** (`PHRF_ROOT_FD`), not through arguments or environment, so `ps` does not show it. The runner must read it once at start and never log it.

## 1. Owner prerequisites (before v0 is committed)

1. **Owner generates the key pair off this machine** (X25519; for example `openssl genpkey -algorithm X25519 -out owner.key` and `openssl pkey -in owner.key -pubout -out owner.pub`). The private key stays with the owner and is not sent anywhere or pasted into any session.
2. Owner provides `owner.pub` (PEM or 64 hex characters).
3. The custodian prints the fingerprint: `python -m phrf_custody fingerprint owner.pub`.
4. **The owner confirms that fingerprint out-of-band** (a channel other than the one that delivered the key). The confirmed string is passed to every `--expect-fingerprint`; sealing refuses on mismatch. Record it and the date in manifest v0.
5. **Owner key unavailable: do not run.** If the owner cannot supply and confirm a public key, or the fingerprint does not match, the pilot does not start. There is no fallback key, no plaintext fallback, and no "seal later".
6. **Key backup and rotation.** The owner keeps at least two independent offline backups of the private key (different media and places) and verifies at least once, before v0, that one backup can unseal a test store made with `phrf_custody seal` on throwaway data. Rotation before the pilot (a new key, a new fingerprint, a new confirmation, a new v0) is cheap and allowed. Rotation after sealing has begun is not done in place: the owner would have to unseal and re-seal, which requires a new owner decision and a custody-log entry. A lost key means the sealed tree and the revealed secret cannot be opened; the pilot is then void.

## 2. Custodian steps, in order

All commands append to `custody.log.jsonl` (`--log`) and print the log head hash. **Anchor the head hash** outside the log after every step (message to the owner, the Mote issue, and manifest v0/v1 at the end); `phrf_custody.log.verify(path, expected_head=...)` then detects truncation or rewriting. The log is locked and fsynced on every append.

1. **Quiesce the machine** (section 5, snapshot "start").
2. **Clean-checkout build.** `python -m phrf_custody checkout <repo> <full 40-hex reviewed SHA> <new checkout dir> stamp.json`. This runs `git clone --no-hardlinks`, `git checkout --detach <SHA>`, and refuses unless HEAD equals the SHA, the tree is clean, there is no tracked symlink or submodule, and no scalafim override is present in the environment (`SBT_OPTS`, `JAVA_OPTS`, `JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS`, `_JAVA_OPTIONS`, `SBT_ARGS`, `JVM_OPTS`), in `.jvmopts`, `.sbtopts`, `.sbt/jvmopts` of the tree, or in the global sbt configuration (`~/.sbtopts`, `~/.jvmopts`, `~/.sbt/**/*.sbt`, `~/.sbt/*/plugins`). It also refuses if the custody tool in use differs from the one at the reviewed SHA. `-Dsbt.global.base`, `-Dsbt.boot.directory` and `-Dsbt.ivy.home` are refused as well, and the clone runs with `-c core.hooksPath=/dev/null` and `--template=` so no global hook or template runs or is copied. The stamp also records the hash of `~/.sbt/repositories` and the HEAD SHA of every staged source-dependency clone under `~/.sbt/*/staging/*/*`, so the dependency sources the build used are pinned. The stamp records the SHA, `build.sbt` hash, `galeRevision` lines, toolchain identities, and the hashes of the custody tool and `requirements.lock`. Build with `python -m phrf_custody build <checkout dir> -- <command>`, which runs under `env -i` with only `PATH HOME JAVA_HOME LANG LC_ALL TERM TMPDIR USER`. The SHA must be the one the separate runner reviewer approved.
3. **Start the session before v0 is written**, under `caffeinate -i -s`, with a **fresh, nonexistent** `--secret-dir`. `python -m phrf_custody session --v0 <v0.json> --repo <repo> --v0-commit <sha> --v0-repo-path <path> --owner-pub owner.pub --expect-fingerprint "<fp>" --secret-dir secret.sealed --beacon-out beacon-A.json --require-online --ack-timeout 600 -- <runner command>` (this is the **real-run command**: `--require-online` refuses the local-clock fallback and `--ack-timeout 600` allows a cold JVM/sbt start; a rehearsal may omit both) generates the secret, seals it to the owner key, prints its commitment, and **stays alive holding the secret only in memory** (it never touches disk in plaintext). **Record the printed anchors off-machine at the moment they appear** (owner, not an agent session; see section 2a): `ANCHOR secret-commit: <seq>:<hash>` is printed and flushed when the secret is committed, and `ANCHOR v0: <seq>:<hash>` when v0 has been accepted. Put the printed commitment in the v0 file. The process then waits for v0. **Crash or rerun while sealing the secret:** `--secret-dir` must not exist, so a rerun is refused up front (it would otherwise append a second, different secret to the same store and make the reveal impossible). If the session died after the store was created and before v0 was committed, nothing is lost: keep the old directory (never delete), start again with a new directory and a new secret, and put the new commitment in v0. If it died after v0 committed the old commitment, use owner-assisted recovery (section 6); if the store was only appended and never closed, the owner opens it with `reveal --allow-partial`. An already-closed store is refused as well.
4. **v0 fixes the beacon round before it is published.** v0 is a JSON file with `beacon_round`, `drand_chain_hash`, `secret_commitment` and `seeds_py_sha256` (and the rest of the manifest). The round A is chosen in v0 **before v0 is published**, far enough ahead that the v0 commit (and its review) precedes the round's time; round time = `1595431050 + 30 * (round - 1)` (UTC epoch). The tooling asserts that the committed v0 equals the working file, that the round and v0 hash used equal the file's, and that **the round's time is later than the v0 commit's committer date**; a violation refuses and voids the pilot. Because the committer date is forgeable, the tool also enforces the ordering **by its own clock**: v0 must be loaded (found committed with this session's commitment) while the current time is before the round's time, otherwise the session logs `v0-late` and refuses; the load time and the round time are logged in the `v0` entry. While waiting for v0 the session logs each distinct waiting reason once (`v0-wait`) and fails at once, logging `v0-refused`, on a permanent error (wrong chain, bad fields, wrong hash or round, round not after the commit, short commit id; `--v0-commit` must be the full 40-hex id). v0 also fixes the chain hash `8990e7a9aaed2ffed73dbd7092123d6f289930540d7651336225dc172e51b2ce` (League of Entropy default, `pedersen-bls-chained`, 30 s), the relays, the reduction (first 8 bytes big-endian of the SHA-256), the denylist rule and the hash of `seeds.py`.
5. **The session then, unattended:** before accepting v0 it asks the relays whether round A is already published (published means `v0-late` and refusal). With **`--require-online`**, which the real run uses, an unreachable network is a refusal too; without it the session logs `round-check-unavailable` and uses the local clock. It then waits until one period after round A, fetches it from at least two relays that must agree, **requires BLS verification** against the chain public key (BLS is the default; `--allow-unverified` exists only for a documented fallback in which verification is by independent re-fetch from two relays by a second party on another network before the run starts), stores and logs the raw responses and their hashes, **re-verifies the stored signature (BLS) when deriving the root**, checks the `seeds.py` hash against v0, derives `root`, runs the denylist check over root64 and all 980 stream seeds, and launches the runner with root64 on an inherited pipe and **requires an acknowledgement**: the runner writes `hex(SHA-256(<line it read>))` to `PHRF_ROOT_ACK_FD` after reading the root (format spec section 8). A runner that exits, even with status 0, without a correct acknowledgement (or does not acknowledge within the timeout, in which case it is killed) is a failed attempt, so the acknowledgement is proof of **receipt of the root by a process holding the ack descriptor** (it does not prove what that process does next). The runner is started in its own process group; on a missing, wrong or late acknowledgement the **whole group is SIGKILLed**, the leader is reaped, and **process-group members are confirmed gone** (by `ps`, counting zombies as gone; not by `killpg` return codes) before any restart, so a wrapper such as `sh -c` or an sbt launcher cannot leave the real runner alive on the store; leftover group members are also killed after every attempt, so a runner must leave no background processes. If members stay alive the session logs a `runner-exit` entry with a note and aborts. **Limit:** a descendant that leaves the process group (`setsid`, double-fork daemonisation) is not covered by this check; the runner contract forbids it. Use `--ack-timeout 600` for a cold JVM/sbt start (the clock runs from launch to the acknowledgement, and the runner must acknowledge immediately after reading the root, before doing any work). **A denylist hit aborts the pilot** and requires an amended v0; never re-derive and never pick another round.
6. **Run the pilot** from the stamped build. The runner writes raw results only through the sealed store (format spec; it reads root64 once from `PHRF_ROOT_FD`, closes the descriptor and unsets the variable before spawning anything); any plaintext spill is a defect. Every blob is decrypted back with its own ephemeral key and compared with the plaintext at write time, before it is published. The runner exits non-zero on failure; `--max-restarts N` relaunches it with the same root (section 6).
7. **Seal and close.** (`phrf_custody seal` on a plaintext directory is **REHEARSAL ONLY**: the real pilot never has a plaintext tree, and the command prints that banner, logs `seal-rehearsal`, and puts no plaintext digest in the log, stdout or `SEALED`.) The runner's store is closed once (`SealedStore.close`) after the last blob; the sealed-tree digest is recorded before the aggregator runs and again after (design 4.3), and they must be equal. If a plaintext directory was used (rehearsals only), `phrf_custody seal <raw> <sealed> owner.pub --expect-fingerprint "<fp>"` seals it, checks the fingerprint before writing anything, compares the plaintext digests before and after internally (they are not recorded anywhere) and records the sealed-tree digest, verifies every blob at write time (decrypt with the ephemeral key, compare with the plaintext, re-read the file), then removes the plaintext. Stale `*.tmp` files from crashed writers are removed at close and are ignored by readers and by the digest.
8. **Release the whitelist.** `phrf_custody release candidate.json pilot-whitelist.json`. The candidate carries per-pair sigma and df; release **pools df to one value (the minimum, refused below 14)**, quantizes floats to **5 significant figures (sigma and the ICC upper limit rounded up)**, validates after rounding, and refuses on any extra, missing or mistyped field. The coverage ICC may be `"degenerate"` (with `ucl80` `"degenerate"`); every ICC carries an F-based 80 % upper limit truncated at 0. On refusal the log and the message name only the top-level section, never keys or values.
9. **Hand over.** To authors: `pilot-whitelist.json`, its SHA-256, the sealed-tree digest, `stamp.json`, the words "run complete", total CPU hours. These and the secret commitment enter manifest v1.
10. **Off-machine copies.** Make **at least two off-machine copies of each of: the sealed results tree, `secret.sealed`, the custody log (with its anchored head hash) and `stamp.json`** (`rsync` of ciphertext and public records only, to two independent locations the owner names). Verify each copy by recomputing the sealed-tree digest (results tree and `secret.sealed`, via `seal.sealed_digest`) and the SHA-256 of the log and stamp, and record all those digests **in manifest v1** and in the log. Losing `secret.sealed` without a copy would make the reveal impossible. Nothing is deleted.
11. **Anchor, then unseal.** The `sealed_tree_digest` of the results tree and of `secret.sealed` must be **anchored out-of-band before any unseal** (manifest v1, the owner's own notes, the Mote issue); the owner unseals only with `--expect-tree-digest <anchored digest>`. The `SEALED` file next to the data proves nothing by itself.
12. **Owner-side unseal and reveal** (off this machine, not before the confirmatory report is closed): `phrf_custody unseal` verifies and decrypts; `phrf_custody reveal secret.sealed owner.key <commitment from v0>` decrypts the sealed secret and checks it against the v0 commitment (a mismatch is refused). The owner can then recompute `root` and compare `sha256(root)` with the custody log's `root` entry.

## 3. What authors and reviewers may see, and the peeking ban

Allowed: the whitelist file, its SHA-256, the sealed-tree digest, the stamp, "run complete", total CPU hours, the secret commitment, and the custody log (it contains no results and no root).

Forbidden for authors, reviewers and every non-custodian agent: opening, listing, `ls -l`, `du`, `stat`, `find` or copying anything under the sealed directory, the runner output directory or the custodian work directory; reading file counts, sizes, modification times or names (ciphertext sizes and the blob count are metadata); reading runner logs, stdout or stderr; attaching to or inspecting custodian processes or their memory; and asking the custodian for any quantity outside the whitelist. **The ban is enforced by this rule plus the audit snapshots of section 5**, not by permissions. A suspected peek is reported to the owner and recorded in the custody log; it is not fixed quietly.

## 4. Authors and other agents do not run during the pilot

From the first step to the hand-over, **no author agent or other agent session runs on the machine** (including build agents, dashboards, indexers and file watchers that touch the work areas). The custodian session is the only agent session. Authors resume only after step 9.

## 5. Audit snapshots

At **start, at each resume after a failure, and at end**, the custodian takes a snapshot:

```
ps -axo pid,ppid,user,lstart,command > snap.txt
lsof -nP +D <runner output dir> >> snap.txt
lsof -nP -c claude -c node -c java -c python >> snap.txt 2>/dev/null
shasum -a 256 snap.txt
```

and appends the **SHA-256 of the snapshot** (and a note of the snapshot file's location) to the custody log; the snapshot files are retained by the custodian. The custodian reads each snapshot and aborts if any process other than the custodian's own and the runner has the runner output directory (sealed store included) open or if another agent session is running. The same rule covers Spotlight (`mdworker` must not hold the runner output directory; see section 0).

## 6. Failure handling

- **Denylist hit:** abort; log; amended v0 required. No re-derivation.
- **Beacon unavailable, relays disagree, or BLS fails:** do not use the round. Retry the same round later (immutable once published); persistent disagreement goes to the owner. Never substitute another round.
- **Dirty tree, wrong HEAD, tracked symlink or submodule, override anywhere, tool mismatch:** the build is refused; fix the cause and clone afresh. A build that already produced results from a refused state is discarded.
- **Fingerprint mismatch or owner key unavailable:** do not run (section 1).
- **Mid-run failure (runner crash, power loss):** take a "resume" snapshot, then **resume under the same encryption**: same owner key, same fingerprint check, same root (the session relaunches the runner with the same pipe-delivered root; the writers are stateless and cannot see what is sealed, so a resumed run recomputes datasets. The S7 runner seals every unit record under a name that carries the invocation's run id, so a resume never repeats a unit name: only `meta/root-check` and `meta/stamp` repeat, as identical copies. The reader refuses differing copies of a repeated name. The owner detects a nondeterministic unit by comparing payload hashes across its commits; see format spec section 10. Every resume is a **new runner process**: a runner instance runs once.) If the session process itself died or the machine rebooted, the secret is gone from memory: **owner-assisted recovery** is the only route. The owner decrypts `secret.sealed` off-machine and starts the new `session ... --secret-stdin` **from the owner's own terminal**, typing the 64 hex characters at a hidden prompt, so the value never passes through an agent session, a tool call, a chat or transcript, a command line, the clipboard, a file, or shell history. In **zsh**: `read -rs "S?secret hex: "; printf '%s\n' "$S" | python -m phrf_custody session ... --secret-stdin ...; unset S`. In **bash**: `read -rsp 'secret hex: ' S; printf '%s\n' "$S" | python -m phrf_custody session ... --secret-stdin ...; unset S`. `read -s` does not echo and does not enter history; `printf` is a shell builtin, so the value is not in any process argument list (`ps`); do not `export S`, and do not paste the value (clipboard managers keep it). If any of those happened, the secret is treated as disclosed and the pilot is void. The recovery is logged as `secret-recovered`. **Recovery re-proves BOTH orderings from the custody log, pinned by owner-held anchors.** `--log-anchor` is **mandatory** with `--secret-stdin` (repeat it for each anchor: `--log-anchor <seq>:<hash>` for the `secret-commit` entry and for the `v0` entry, exactly as printed and recorded by the owner). The session refuses unless the verified log still contains those exact entries (a rewritten or re-chained log cannot reproduce them, and they stay valid however many entries were appended afterwards), the anchored `secret-commit` entry carries this commitment and is earlier than round A, and the anchored `v0` entry carries this v0 hash and was loaded before round A. Consequently a crash during `v0-wait` (no `v0` entry exists) followed by a v0 committed after round A is public cannot be recovered: the pilot is void and needs an amended v0 and a new secret. `--log-anchor` is refused on a fresh (non-recovery) session. **A second recovery must again use the ORIGINAL `v0` anchor** (and the original `secret-commit` anchor): the recovered `v0` entry carries the original `loaded_at` but a late `ts`, so its own anchor is for audit only and is refused as a recovery proof. The recovered `v0` entry records `method: log+anchors`, the original `loaded_at`, `network_checked` as originally observed, `recovered_at`, and prints its own anchor. The CLI rejects a recovered secret that is not exactly 32 bytes. If the owner is not available, the pilot is void.
- **Resume cost and the CPU ceiling.** A resumed runner skips the completed jobs. The invocation that reaches an accepted decision then recomputes, once, every kept job completed by an earlier invocation, so that the in-process scorer has them. The recomputation is sealed under `rerun/<runId>/...` and is never scored, and its CPU counts toward the cumulative guard. A crash late in the pilot can therefore push the total past the hard ceiling. That requires an owner-approved raise, logged like any other. A resume refuses if `cost.json` is missing or unreadable while progress or sealed blobs exist. Never recreate `cost.json` by hand: report it to the owner.
- **Partial seal.** If the run cannot be completed, the store is closed as it is only under the **uniform drop rule** (design F9: round-robin dispatch, uniform reverse-index drop, df and UCL recomputed, refusal at D < 15). A store without a CLOSE record is opened by the owner only with an explicit allow-partial decision, recorded in the log.
- **Source changed during sealing, or write-time read-back failed:** the store or `seal` aborts, nothing is published or the plaintext is kept; rerun after finding the cause.
- **Custody log with a truncated final line (crash mid-append):** `append` refuses (`LogCorrupt`). Run `phrf_custody log-repair` as an explicit step: the partial tail is moved to `custody.log.jsonl.tail-<ts>` (kept, never deleted), the earlier chain must still verify, and a `tail-repaired` entry records the size and SHA-256 of what was removed. Re-anchor the new head hash. The log also refuses timestamps that go backwards.

## 2a. Anchors the owner must record off-machine

The session prints two lines that the **owner records off-machine (paper or the owner's own device, not an agent session or this machine) at the time they are printed**: `ANCHOR secret-commit: <seq>:<hash>` and `ANCHOR v0: <seq>:<hash>` (a recovered session prints a new `ANCHOR v0` too). Also record the `log head:` line printed after every action. Anchors are what make recovery and later audits trustworthy; without them a writer of the log could forge entries and re-chain it. Read the anchors **from the real terminal output or from the real `custody.log.jsonl` yourself, never from an agent's relay or summary** (an agent could mistype or substitute them). Check at the end that the real run's `v0` entry shows `network_checked: true` (`--require-online` enforces it, and in recovery it requires the **original** v0 entry to show `network_checked: true`).

## 7. Tooling self-checks before v0

Run the custody test suite from the reviewed checkout (`python3.12 -m pytest -q -p no:cacheprovider tests`) with `py-ecc` installed, record the counts in the stamp notes, and confirm the published known-answer tests pass (RFC 7748 section 6.1 X25519, RFC 5869 appendix A.1 and A.3 HKDF-SHA256, `tests/test_kats.py`) next to the self-generated sealed-format vectors. The owner uses `unseal --expect-tree-digest <anchored digest>` so a store is checked against the out-of-band anchor.
- **Whitelist rejected, or pooled df < 14:** the aggregator has a defect or the pilot is too thin. The custodian reports only "whitelist rejected" with the top-level section name. The aggregator is fixed and reviewed; any rerun is from sealed inputs only if the runner reviewer agrees.
- **Custody log chain broken or head not matching the anchor:** treat all later results as unverified and report to the owner.
